Техническая инструкция: Интеграция онлайн-оплаты

Цель: Обеспечить безопасный, надежный и масштабируемый процесс оплаты на интернет-магазине, минимизируя риски и повышая конверсию.

Целевая аудитория: Backend и Frontend разработчики.

⚙️ Шаг 1: Выбор и настройка платежной системы

Действия:

  1. Выбор провайдера: Выбор платежной системы (Stripe, ЮKassa, СберAPI и т.д.) на основе требований к регионам, валютам и типу бизнеса.
  2. Получение ключей: Регистрация аккаунта и получение необходимых ключей: API Key (Secret) и Merchant ID.
  3. Тестирование: Использование тестового режима (Sandbox) для всех интеграционных тестов.

Требуемые данные: API_KEY, MERCHANT_ID, WEBHOOK_URL (адрес, куда платежная система будет отправлять уведомления об успехе/провале).

🖥️ Шаг 2: Frontend — Создание формы оплаты

Цель: Сбор всех данных покупателя и безопасная токенизация платежных данных.

Технологии: React/Next.js, виджеты платежной системы (например, Stripe Elements).

Элементы формы:

  • Данные заказа: ID заказа, Сумма (получены из контекста/роута).
  • Данные покупателя: Email, Имя, Телефон.
  • Платежные данные: Поле для ввода карты. Важно: Данные карты никогда не должны обрабатываться на нашем сервере, только через виджет платежной системы.

Логика: При клике на "Оплатить" происходит вызов функции, которая отправляет данные на наш Backend API, передавая только токен платежа.

⚙️ Шаг 3: Backend — Обработка запроса и создание платежа

Эндпоинт: POST /api/payment/process

Входящие данные (Payload):

{ "orderId": "ORD-12345", "amount": 15000, "token": "mock_token_xyz", "buyerEmail": "user@example.com" }

Логика Backend (Пошаговый алгоритм):

  1. Валидация: Проверить существование заказа и его статус (должен быть CREATED).
  2. Вызов Gateway: Вызвать API платежной системы с полученным токеном и суммой.
  3. Обработка ответа: Если платеж успешен, получить Transaction ID.
  4. Обновление БД: Обновить статус заказа в базе данных на PAID и записать Transaction ID.

🔄 Шаг 4: Обработка ответов и уведомления

Сценарий 1: Успех (Success)

  • Backend: Обновление статуса на PAID.
  • Backend: Отправка уведомления в CRM/ERP.
  • Frontend: Получение ответа {success: true, transactionId: ...}. Отображение зеленого сообщения об успехе.
  • Пользователь: Получает подтверждение на email.

Сценарий 2: Провал (Failure)

  • Backend: Обновление статуса на FAILED.
  • Frontend: Получение ответа {success: false, message: "Недостаточно средств"}. Отображение красного сообщения с причиной.

✨ Заключение

Благодаря модульному подходу, мы отделили бизнес-логику (paymentService) от UI и внешних интеграций (paymentGateway), что обеспечивает высокую тестируемость, надежность и простоту масштабирования системы.
